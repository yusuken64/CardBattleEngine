Title:
GameEngine.Resolve: central interception — pause and prompt for any action whose PendingTargetRequirement isn't yet satisfied

Purpose:
This is the single choke point for the entire redesign. `GameEngine.Resolve`'s `_actionQueue` while-loop is the one place every action passes through, regardless of origin (top-level player choice, a Pre/Post trigger, or a side-effect any action yields). Adding one check here — "does this action need targets it doesn't have yet?" — makes target-requesting work uniformly for card plays AND triggered abilities, with no special-casing needed anywhere else in the engine.

Dependencies:
NTR-001, NTR-003

Consumes:
NTR-001: `ActionContext.PendingTargetRequirement`, `TargetRequirement`. NTR-003: `TargetSelectionChoice`.

Produces:
The central pause/resume behavior that every other Phase B/C task relies on: NTR-007 (multi-target card plays), NTR-013 (triggered abilities), and both Phase C proof-of-concept tests depend on this check existing and being correctly ordered.

Files:
CardBattleEngine\Engine\GameEngine.cs

Requirements:
In `GameEngine.Resolve`, inside the `while (_actionQueue.Count > 0)` loop, insert a new check immediately after dequeuing `current` and BEFORE the existing `if (!current.action.IsValid(...)) continue;` line. The ordering matters: this check must run before `IsValid`, before the `OriginalAction` assignment, and before Pre-triggers — so that nothing in the resolution chain (validity checks, pre-triggers) ever sees a partially-filled `Targets` list; everything downstream of this check can assume `Targets` is already complete.

```csharp
while (_actionQueue.Count > 0)
{
    (IGameAction action, ActionContext context) current = _actionQueue.Dequeue();

    if (current.context.PendingTargetRequirement is { } requirement &&
        (current.context.Targets == null || current.context.Targets.Count < requirement.Count))
    {
        gameState.PendingChoice = new TargetSelectionChoice
        {
            SourcePlayer = current.context.SourcePlayer,
            PendingAction = current.action,
            PendingContext = current.context,
            Requirement = requirement,
            PickedSoFar = new List<IGameEntity>(),
        };
        return;
    }

    // ... existing code below this point is UNCHANGED: IsValid check, OriginalAction assignment,
    // Pre-triggers, Canceled check, ResolveAction, Post-triggers, side-effect enqueueing ...
}
```
Do not move, remove, or reorder anything below this insertion. The `return;` is intentional and important: it leaves the `while` loop (and the surrounding `Resolve` method) entirely, WITHOUT re-enqueueing `current` — `current` is now tracked via `gameState.PendingChoice.PendingAction`/`PendingContext` instead of the queue. Any OTHER items still sitting in `_actionQueue` (from earlier in this same resolution chain) remain queued, since `_actionQueue` is an instance field on `GameEngine`, not a local variable — they will be processed on the next call to `Resolve()`, whenever that happens (e.g., when the player supplies a target via a `SupplyTargetAction`, which is itself resolved through a fresh top-level `Resolve()` call).

Constraints:
- Scope this diff to exactly this one insertion in this one file.
- Do not change anything about the existing pre-trigger, post-trigger, `IsAllowedChoice`, or `ResolveAction` logic.
- Do not add any card-specific or trigger-specific logic here — this check must be completely agnostic of what `current.action` is.
- Do not add a null-check workaround that treats a missing `PendingTargetRequirement` as anything other than "this action doesn't need interactive targeting, proceed as before" — every existing action (whose `ActionContext` never sets `PendingTargetRequirement`) must be completely unaffected by this change.

Acceptance Criteria:
- Every existing action (which never sets `PendingTargetRequirement`) resolves exactly as before — zero behavior change.
- An action whose `context.PendingTargetRequirement` requires more targets than `context.Targets` currently holds causes `Resolve` to install a `TargetSelectionChoice` as `gameState.PendingChoice` and return immediately, without resolving that action, without running its pre-triggers, and without disturbing any other items already queued.
- Once the player supplies enough targets (via `SupplyTargetAction`, task NTR-004) and the original action is re-enqueued with a full `Targets` list, it proceeds through the completely unchanged `IsValid` → Pre-triggers → resolve → Post-triggers pipeline exactly like any other action.
