Title:
GameState.GetValidActions: for multi-target cards, offer PlayCardAction with an attached PendingTargetRequirement instead of flattening a cross-product

Purpose:
For a card requiring more than one target, the existing cross-product flattening (one action per single candidate) can't express "pick 2 of these." Instead of a bespoke "begin selection" action (the earlier, now-abandoned design), this task offers the real `PlayCardAction` directly with `Targets` left unset and `context.PendingTargetRequirement` populated — the generic central interception added in NTR-005 automatically pauses and prompts once that action is dequeued.

Dependencies:
FWD-009, NTR-001, NTR-006

Consumes:
FWD-009: mechanically-renamed `GameState.cs` (sequencing after it avoids merge conflicts on the same file). NTR-001: `TargetRequirement`/`ActionContext.PendingTargetRequirement`. NTR-006: `Card.RequiredTargetCount`/`Card.AllowDuplicateTargets`.

Produces:
The multi-target card-offering branch, exercised end-to-end by the POC-002 test.

Files:
CardBattleEngine\Engine\GameState.cs

Requirements:
Inside `GetValidActions`, in the `foreach (var card in player.Hand)` block, locate the point right after the existing `WeaponCard` special-case handling and right before the existing single-target flattening loop (the one that computes `validTargets = playCardAction.Card.ValidTargetSelector?.Select(...)` and adds one action per candidate). Insert:
```csharp
if (card.RequiredTargetCount > 1)
{
    actions.Add((
        new PlayCardAction { Card = card },
        new ActionContext
        {
            SourcePlayer = player,
            Source = card,
            SourceCard = card,
            PendingTargetRequirement = new TargetRequirement
            {
                Provider = card.ValidTargetSelector,
                Count = card.RequiredTargetCount,
                AllowDuplicateTargets = card.AllowDuplicateTargets,
            },
        }));
    continue;
}
```
(Adjust variable names — `actions`, `player`, `card` — to match whatever the surrounding loop actually uses; this is illustrative of the exact insertion point and logic, not necessarily byte-for-byte matching existing identifier names.) Everything below this insertion (the existing single-target flattening loop) must remain completely untouched — cards with `RequiredTargetCount == 1` (the default, i.e. every existing card) keep going through the pre-existing per-candidate flattening exactly as before, since that flattening is still correct and cheaper for the single-target case (no need to pause when the candidate is already known at menu-build time).

Constraints:
- Scope this diff to exactly this one insertion in this one file.
- Do not modify the existing single-target loop, the attack-enumeration logic, or the `PendingChoice` short-circuit at the top of the method.
- Do not reference `TargetSelectionChoice`, `SupplyTargetAction`, or any "begin selection" action here — the generic pause happens automatically inside `GameEngine.Resolve` (NTR-005) once this `PlayCardAction` is dequeued; `GetValidActions` only needs to attach the requirement, nothing else.

Acceptance Criteria:
- For a card with `RequiredTargetCount > 1`, `GetValidActions` returns exactly one `(PlayCardAction, ActionContext)` pair for that card, with `Targets` unset and `PendingTargetRequirement` populated from the card's own `ValidTargetSelector`/`RequiredTargetCount`/`AllowDuplicateTargets` — not a flattened cross-product, and not a bespoke "begin" action.
- For every existing card (`RequiredTargetCount == 1`, the default), `GetValidActions`'s output is byte-for-byte identical to before this change.
